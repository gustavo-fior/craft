# Internationalization

English is the source language. Spanish (Spain) is the first translation, not a limit on supported languages. The interface locale comes from the URL: English keeps the existing unprefixed routes, and other registered locales use a prefix such as `/es/tabular-numbers`. Language selection does not depend on a browser-language redirect or a cookie.

## Content availability

An article can be missing in a language without blocking that language's navigation or publication. The selected interface stays in that language, while the article resolves independently:

| Translation | Article shown | Editorial status |
| --- | --- | --- |
| Missing | English original | Visible notice explains the fallback. |
| Present, reviewed against the current source | Translation | Current. |
| Present, source changed since review | Translation | Notice links to the latest English original. |

Missing translations remain visible in the index with an English-language label. An outdated translation is retained; a changed hash is a review request, not evidence that every translated sentence is wrong.

`src/i18n/content.ts` resolves this state. `src/i18n/source-revision.ts` hashes the complete original MDX file, including frontmatter, after normalizing CRLF to LF. Any other source change, including whitespace, changes the hash.

## Check translation status

Run from the project root:

```sh
bun scripts/translation-status.ts
```

To inspect Spanish only:

```sh
bun scripts/translation-status.ts es
```

The read-only report lists every original, including unpublished articles, with `missing`, `current`, or `outdated` for each selected locale and the full source SHA256. English is always current. It reads MDX files directly and works before a build; generated content collections are not required. Missing and outdated translations are expected editorial states and return exit code 0. Invalid arguments, unreadable files, or malformed revision metadata return exit code 1.

The report never changes translation metadata. A matching hash records which source was reviewed; it does not establish translation quality.

## Add a language

1. Add its route locale to `locales` in `src/i18n/locales.ts` and provide its native name, BCP 47 language tag, Open Graph locale and text direction in `localeDetails`. Use the intended regional variety where appropriate, such as `es-ES`. Routing and generated locale paths derive from this registry.
2. Add complete interface and static-page catalogs, following `src/i18n/ui.ts`, `src/i18n/ui.server.ts` and `src/i18n/messages/en-pages.ts`. Register them in the server catalog map. Interface messages use `UiMessages`; static pages use `PageMessages`, keyed by `PageCopyKey` from the English catalog. Use stable semantic keys such as `home.introduction` and `resources.description`, so editing English copy does not rename a message. Do not replace these types with partial catalogs to silence missing-key errors. Include navigation, notices, search, accessibility labels, Markdown labels and metadata descriptions. Copy proper names unchanged where appropriate, but include every required key.
3. Add reviewed articles under `content/<locale>/<section>/<slug>.mdx`. Launching the language does not require translating every article; absent articles use the documented English fallback.
4. For each translated article, add its demo catalog at `src/i18n/demos/<locale>/<slug>.json`, even if it is empty. The server loads the active article's catalog, so a translated article with no catalog is a packaging error. Shared labels such as Wrong, Right and Guides come from the interface catalog.
5. Run the status report, type checks, build and the accessibility/SEO checks below before publishing.

Do not add language-specific conditionals to demos or routing. Add the locale's data to the registries and catalogs instead. For a right-to-left locale, review layouts and directional icons as well as setting text direction; a `dir` attribute alone does not verify the experience.

## Translate or update an article

Read the entire English article and exercise its demos before translating. Preserve the explanation's meaning, qualifications, examples and technical distinctions. Spanish uses Spain vocabulary and natural direct address. Keep established technical terms in English when that is clearer, with a Spanish explanation in parentheses on first use when useful. Do not translate identifiers or substitute a different technical concept to make a sentence sound smoother.

Keep the source filename, slug, section enum, order and publication date. Translate the title, description, body and resource descriptions. Preserve URLs, code samples and component names. Proper names and cited work titles can stay in their original language. Localize visible demo labels, sample prose, accessible names and status messages through `useDemoText`; preserve state values, CSS and program identifiers. Keep translated units and numbers appropriate to the selected locale.

Add translation frontmatter alongside the original fields:

```yaml
locale: es
translatedAt: "2026-09-19"
sourceRevision: "<full source SHA256 from the status report>"
```

Use the date of the actual review and the hash of the exact English revision reviewed. Update these fields only after comparing the translation with that revision. Never copy a new hash merely to clear an outdated notice. If the source changes during translation, review the new differences before recording its hash.

Demo catalogs map an English source string to translated text. Preserve interpolation names such as `{count}`. Resolve complete phrases, rather than concatenating fragments that assume English word order. Code examples intentionally remain English. Verify that code regions containing English prose have `lang="en"`, while translated controls such as Copy keep their interface language.

## Accessibility, SEO and performance checks

- Verify the document's interface language and direction. For English fallback content, verify that the article's language remains English and the missing-translation notice is in the interface language. Mark other substantial language changes explicitly.
- Exercise the language selector with the keyboard, including focus, selected language and Escape. Check translated accessible names, mobile text overflow and language changes with a screen reader.
- Verify current, missing and outdated articles separately. A real translation has its own canonical URL and reciprocal `hreflang` alternatives. An English fallback in a localized shell points its canonical to the English original and is not advertised as a translation in `hreflang` or the sitemap. Canonical is a search-engine preference, not an indexing guarantee.
- Verify metadata, Open Graph output and both `.md` routes and `Accept: text/markdown` responses. Their language and status should agree with the article being served.
- When adding or removing a translation, inspect the generated article, alternatives, sitemap and metadata together in a fresh build. Confirm the deployment serves that build rather than stale cached output.
- Keep article resolution and catalogs on the server. Generate the locale routes at build time and send only the active article's demo messages to the browser. Check the build's route output and client payload; do not assume that using an i18n library guarantees static rendering or a small bundle.

The implementation entry points are `content-collections.ts`, `src/i18n/`, `src/app/[locale]/`, `src/app/sitemap.ts` and `src/proxy.ts`. For a new language, verify the actual output in addition to checking that its catalog is complete.
